## 1. What is the difference between WHERE and HAVING?

### Quick Summary
- `WHERE` filters **individual rows** *before* any grouping or aggregation takes place.
- `HAVING` filters **aggregated groups** *after* the `GROUP BY` clause is evaluated.

### Comparison Table

| Feature | WHERE Clause | HAVING Clause |
| :--- | :--- | :--- |
| **Execution Point** | Before `GROUP BY` | After `GROUP BY` |
| **Applicable Target** | Individual rows | Aggregated groups / summaries |
| **Aggregate Functions** | **Cannot** contain aggregates (`SUM`, `COUNT`, `AVG`) | **Can** and typically contains aggregate functions |
| **Usage without GROUP BY**| Fully supported and standard | Can be used, but acts like WHERE on the whole table |
| **Performance** | More efficient (reduces rows early) | Evaluates after aggregation |

### SQL Example

```sql
-- Problem: Find product categories where total sales exceed $1,000, 
-- but only consider non-cancelled orders.

SELECT 
    p.category,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM products p
JOIN order_items oi ON p.product_id = oi.product_id
JOIN orders o ON oi.order_id = o.order_id
WHERE o.order_status != 'Cancelled'             -- Filter rows BEFORE aggregation
GROUP BY p.category
HAVING SUM(oi.quantity * oi.unit_price) > 1000; -- Filter groups AFTER aggregation
```

## 2. What are the different types of joins?

### Quick Summary
Joins combine columns from one or more tables based on a related column between them (typically Primary Key to Foreign Key relationships).

### The Primary Join Types

1. **`INNER JOIN`**: Returns only rows with matching values in **both** tables. Non-matching rows from either table are discarded.
2. **`LEFT JOIN` (LEFT OUTER JOIN)**: Returns **all** rows from the left table and matched rows from the right table. If no match exists, `NULL` values appear for the right table columns.
3. **`RIGHT JOIN` (RIGHT OUTER JOIN)**: Returns **all** rows from the right table and matched rows from the left table.
   > **SQLite Note:** SQLite does not natively support `RIGHT JOIN`. Instead, the same result is achieved by swapping the table positions in a `LEFT JOIN`:  
   > `TableA RIGHT JOIN TableB` $\equiv$ `TableB LEFT JOIN TableA`.
4. **`FULL OUTER JOIN`**: Returns all records when there is a match in either the left or the right table. Unmatched records on either side are filled with `NULL`.
5. **`CROSS JOIN`**: Produces a Cartesian product (combines every row of table A with every row of table B).

### Visual Comparison

```text
    INNER JOIN              LEFT JOIN              RIGHT JOIN (Swapped LEFT)
   [   (   )   ]          [ (*** (   )   ]              [   (   ) ***) ]
    Matched Only           All Left + Match               All Right + Match
```

### SQL Example: Finding Customers with and without Orders

```sql
-- INNER JOIN: Only buyers who placed at least one order
SELECT c.customer_name, o.order_id, o.order_date
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: All customers, revealing inactive accounts with NULL order_id
SELECT c.customer_name, o.order_id, o.order_status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;
```

## 3. How do you calculate average revenue per user (ARPU) in SQL?

### Quick Summary
**Average Revenue Per User (ARPU)** is a fundamental business metric that measures the average monetary amount generated by each customer.

$$\text{ARPU} = \frac{\text{Total Net Revenue}}{\text{Count of Active Paying Customers}}$$

### Step-by-Step Implementation

1. **Inner Step:** Calculate the total revenue generated by each customer using `SUM(quantity * unit_price)` grouped by `customer_id`. Exclude cancelled orders.
2. **Outer Step:** Use the inner aggregated result as a **derived table** and compute `AVG(customer_revenue)`.

### SQL Example

```sql
SELECT 
    COUNT(customer_id)              AS active_customers,
    ROUND(SUM(customer_revenue), 2) AS total_revenue,
    ROUND(AVG(customer_revenue), 2) AS average_revenue_per_user
FROM (
    SELECT 
        o.customer_id,
        SUM(oi.quantity * oi.unit_price) AS customer_revenue
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.order_status != 'Cancelled'
    GROUP BY o.customer_id
);
```

*Result in this project:* **$636.66** per paying customer across 14 customers ($8,913.30 total revenue).

## 4. What are subqueries?

### Quick Summary
A **subquery** (or nested query / inner query) is an SQL query embedded inside another SQL statement (`SELECT`, `INSERT`, `UPDATE`, `FROM`, `WHERE`, `HAVING`).

### Types of Subqueries

1. **Scalar Subquery**: Returns exactly one single value (one row, one column). Often used in `SELECT` or `WHERE` comparisons.
2. **Multi-Row Subquery**: Returns multiple values (one column, multiple rows). Used with `IN`, `NOT IN`, `ANY`, `ALL`.
3. **Correlated Subquery**: References columns from the parent (outer) query. It executes repeatedly once for every candidate row evaluated by the outer query.
4. **Derived Table (Inline View)**: A subquery inside the `FROM` clause that functions as a temporary in-memory table.

### Practical Examples

```sql
-- 1. Scalar Subquery: Find products priced above catalog average
SELECT product_name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- 2. Multi-Row Subquery: Find customers who never ordered
SELECT customer_name, email
FROM customers
WHERE customer_id NOT IN (SELECT DISTINCT customer_id FROM orders);

-- 3. Correlated Subquery: Show order count for each customer
SELECT 
    c.customer_name,
    (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS total_orders
FROM customers c;
```

## 5. How do you optimize a SQL query?

### Quick Summary
Query optimization involves structuring database schemas, queries, and execution plans so that data retrieval uses minimal CPU, memory, and disk I/O.

### Top Optimization Strategies

1. **Use Strategic Indexes:**
   - Index columns frequently used in `JOIN` conditions (Foreign Keys).
   - Index columns frequently filtered in `WHERE` clauses (e.g., `order_date`, `category`).
   - *Result:* Replaces full table scans ($O(N)$) with B-Tree index lookups ($O(\log N)$).
2. **Avoid `SELECT *`:**
   - Retrieve only the specific columns needed. This reduces network payload, I/O memory bandwidth, and allows index-only scans (covering indexes).
3. **Filter Early:**
   - Place restrictive conditions in the `WHERE` clause before `GROUP BY` or multi-table joins to shrink intermediate datasets early.
4. **Use `UNION ALL` instead of `UNION`:**
   - `UNION` forces a costly sorting and deduplication step. If duplicates do not exist or are acceptable, `UNION ALL` runs much faster.
5. **Analyze with `EXPLAIN QUERY PLAN`:**
   - Always inspect the execution plan to verify whether the query planner is using indexes (`SEARCH TABLE USING INDEX`) or reading every single row (`SCAN TABLE`).

### Demonstrating EXPLAIN QUERY PLAN

```sql
-- Before Index on orders(customer_id):
-- Plan: SCAN orders (Reads all 32 rows sequentially)

-- Create Index:
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- After Index:
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 7;
-- Plan: SEARCH orders USING INDEX idx_orders_customer_id (customer_id=?)
```

## 6. What is a view in SQL?

### Quick Summary
A **View** is a saved, named virtual table defined by an underlying SQL query. Views do not store physical data on disk (in standard SQL); instead, the database engine executes the view's query dynamically whenever it is referenced.

### Why Use Views?

1. **Simplification:** Encapsulates complex joins, aggregations, and business logic into a single virtual table name for analysts.
2. **Security & Data Masking:** Grants access to aggregated metrics without exposing sensitive columns (e.g., credit card numbers or passwords).
3. **Consistency:** Establishes a single source of truth for critical KPIs (e.g., revenue definition).
4. **Modularity:** Upstream query changes can be updated once inside the view definition without breaking external reports.

### View vs Materialized View

- **Standard View (Virtual):** Recomputed on every query. Uses zero disk space, always contains real-time data, but may be slow for heavy calculations.
- **Materialized View:** Stores the query result physically on disk. Fast to read, but requires scheduled refresh mechanisms to stay updated.

### SQL Example

```sql
-- Creating an analytical view
CREATE VIEW customer_revenue_view AS
SELECT 
    c.customer_id,
    c.customer_name,
    COUNT(DISTINCT o.order_id) AS total_orders,
    COALESCE(ROUND(SUM(oi.quantity * oi.unit_price), 2), 0.00) AS total_revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.order_status != 'Cancelled'
LEFT JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY c.customer_id, c.customer_name;

-- Querying the view just like a physical table
SELECT * 
FROM customer_revenue_view 
ORDER BY total_revenue DESC 
LIMIT 5;
```

## 7. How would you handle NULL values in SQL?

### Quick Summary
In relational databases, `NULL` does **not** represent zero (`0`) or an empty string (`""`). It represents an **unknown, missing, or inapplicable** value.

### Key Rules for Handling NULLs

1. **Never use `=` or `!=` with NULL:**
   - Any direct comparison with `NULL` returns `UNKNOWN` (falsy in boolean logic).
   - **Correct:** `WHERE column IS NULL` or `WHERE column IS NOT NULL`.
2. **Use `COALESCE()` to provide fallback defaults:**
   - Returns the first non-null argument in a provided list.
3. **Use `IFNULL()` (SQLite / MySQL):**
   - Takes two arguments: returns the first if non-null, else the second.
4. **Understand Aggregate Function Behavior:**
   - Functions like `COUNT(column)`, `AVG(column)`, and `SUM(column)` automatically ignore `NULL` values.
   - `COUNT(*)` counts all rows including those with `NULL` values.

### SQL Examples

```sql
-- 1. Identify missing data
SELECT customer_name, email 
FROM customers 
WHERE city IS NULL;

-- 2. Clean display using COALESCE
SELECT 
    customer_name,
    COALESCE(city, 'Unassigned City') AS clean_city,
    COALESCE(country, 'Global')       AS clean_country
FROM customers;

-- 3. Preventing NULL propagation in revenue math
SELECT 
    c.customer_name,
    COALESCE(SUM(oi.quantity * oi.unit_price), 0.00) AS safe_revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
LEFT JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY c.customer_name;
```
